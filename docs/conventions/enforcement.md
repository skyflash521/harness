# 守らせる機構の規約

`plugins/<プラグイン名>/` 配下へ、エージェントが従うべき定めを新設・変更するとき、**機構が要るか、
要るならどの機構が保証するかの正本**とする。既存の定めの言い換え・参照の追随は対象外。

## 1. 機構が要るかは、破ったときの悪影響で決める

**破ったときの悪影響が無い、またはごく軽微で復旧できるなら、
守らせる機構は要らない。** 機構が要るのは、破った結果が次のいずれかに当たるときである。

- **取り消せない。** 外部への公開・配信・プッシュ、追跡外ファイルの破棄、履歴の書き換え。
- **成果物に残り、後から読む者を誤らせる。** 混入した記述、正本どうしの食い違い、裏取りの無い数値。
- **判定を偽る。** 収束していないものを収束として扱う、確かめていないものを確かめたとして扱う。
- **ユーザーが手を入れるまで作業が進まない。** 止まるべきでない所で止まる、背景処理を待たずに手番を返す。

いずれにも当たらない規律——手順の順序や道具の選び方のように、抜かしても取り直せば済むもの——は
機構を持たなくてよい。`docs/guidance/` に置くか、スキル文書へ手順として書く。**機構が要らないことは、
守らなくてよいことではない。**

## 2. 機構が要る規律を、読まれることだけに依存させない

`docs/guidance/` に置いた規約も、スキル文書・エージェント定義に書いた定めも、当人が読むかどうかに
依存する。[§1](#1-機構が要るかは破ったときの悪影響で決める)で機構が要ると判断した規律を、この層だけで
完結させない。守らせ方は次のどちらかである。

- **機械**: フック・契約スクリプト・検査スクリプト・CI。ツール呼び出しとターン終了を起点に弾く。
- **他エージェント**: `docs/rules/` に節として置き、レビューの常設観点かレビュー専用エージェントの
  定義が、その節を名指しで参照する。

どちらも当てられないなら、その規律を足さずに止めてユーザーに諮る。

## 3. 機械を先に検討する

**フックが最善**、次が検査スクリプトと CI、**レビューは次善**——依頼文へ観点を載せる工程を踏まない
経路には届かない。

上位の手段を採らないと決めてよいのは、[§4](#4-経路ではなく発火を確かめる)の確認で、上位の機構の
起点が無いか、起点は在っても違反を判定しきれないと分かったときに限る。手間の大小で決めない。

## 4. 経路ではなく発火を確かめる

参照経路が在ることは強制ではない。**その規律が問う場面で、その機構が起動するか**を確かめる。

- 起点の無い失敗には、まず起点を作れないかを見る。ツールを呼ばずにターンを終える失敗は、ツール
  呼び出しを起点とする機構には掛からない。
- レビューへ載せるなら、その規律が問う対象が差分に現れることを確かめる。着手しなかった作業や、
  止まらずに進んだ判断は、レビュアーの入力に無い。
