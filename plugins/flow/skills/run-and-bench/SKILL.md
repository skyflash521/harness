# 計測・ツール実行の規律

対象ツールの起動方法・実行環境・既定値は、スキルではなくそのリポジトリの正本ドキュメントを都度参照する。

## 導入契約の確認(最初に行う)

本スキルの実行を開始したら、他の何よりも先に[導入契約の確認スクリプト](../../contract/check_adoption.py)を
絶対パスで実行する。**このスキルファイルから見て `../../contract/check_adoption.py` にある**。

```sh
python3 <check_adoption.py の絶対パス>
```

**非0で終わったら、その出力をそのまま示して停止し、[導入契約](../../docs/rules/adoption.md)へ案内する。**

## 鉄則(最優先)

1. **こけているタスクを待ち続けない。** 前景で実行し、exit code と出力の実体を見てから成否を判断する。
   外枠の `exit 0` や背景タスクの完了通知を成功と誤認しない(中のコマンドが失敗しても外枠は 0 を返す)。
   **待つと決める前に、自分で取り直す費用と待ち続ける費用を比べる。** 取り直しが短時間で済むなら
   待たない。待つと決めたら、**何の完了を待つか**と**いつ・どの条件で再開するか**を書く。書けないなら、
   それは待ちではなく停止である。待つ対象が検査でも計測でもレビューでも規律は同じ。
2. **既知の失敗を繰り返さない。** 実行前に[既知の失敗チェックリスト](#既知の失敗チェックリスト着手前に1回なぞる)を1回なぞる。同じ轍を二度踏まない。
3. **長時間処理の上限と kill はコマンド自身の中に持つ。** 外側ランナー(ハーネスの実行ツール)の timeout パラメータや
   自動背景化に頼らない(背景化した子プロセスはオーファン化して kill しきれないことがある)。重い処理と判断した
   コマンドは、同梱の [run_capped.py](run_capped.py) で包む(**このスキルファイルと同じディレクトリに
   ある run_capped.py を絶対パスで** `python3 <run_capped.py の絶対パス> <上限秒数> -- <コマンド...>`
   の形で実行する)。上限到達時は子プロセスの停止を試み、kill の成否によらず終了コード 124 で呼び出し側へ復帰する。

## ツール実行

- **起動コマンドや実行環境を推測で決めない。** エントリポイント・使う仮想環境・引数を正本で裏取りしてから走らせる。
- **前景で実行し実体で検証する。** そのシェル/ランナーで**正しい exit code を明示表示**し(exit code の
  取り方はシェルにより異なる。成否真偽と取り違えない)、生成物の実体(サイズ・更新時刻)を確認してから
  報告する。投げっぱなしにせず、**結論を先に書かない**。
- **独立して取り直せる処理を1コマンドへ束ねず、出力を握り潰さない。**
- **「実行中」はプロセスの生存か進行中の出力を見てから言う。** 出力が無いことは実行中を示さない。
  観測していないなら未検証と明記し、取り直す費用が小さいなら待たずに取り直す。
  **完了通知は届かないことがある。** 届かなくても再開できる経路を張るか、張らないなら待たずに
  取り直す。
- **生成物はユーザーが見える場所に置く。** scratchpad / temp はユーザーから不可視。視聴・確認用は
  プロジェクトの所定ディレクトリにコピーする。
- **使い捨ての計測・検証スクリプト自体はリポジトリ直下の `.scratch/` に置く**(正本は
  [作業過程の産物を追跡下に残さない](../../docs/rules/artifact-hygiene.md#6-作業過程の産物を追跡下に残さない))。
  上の「生成物は可視の場所へ」とは別物——`.scratch/` はスクリプトそのものの置き場で
  あり、視聴対象にはしない。
- **ユーザーの画面・入力を奪う手段で測らない**(実マウス・実キーボード操作でデスクトップを
  占有する計測も、「操作を控えてください」と依頼して測る形も同じ)。占有せずに測る手段が無いなら、測らずに
  判断へ進む([着手・継続判断規約](../../docs/guidance/work-justification.md#3-原因を裏取りしてから対策を書く))。
- **コード変更中にベースライン/対策版を走らせない。** 走行を止め、安定状態で取り直す。
- **踏んだ不具合を自分の道具側の迂回で終わらせない。** 実行・動作確認で対象側の不具合を踏んだとき、
  自分のスクリプト・手順の側で避けて先へ進むこと自体はよいが、**避けたことはその不具合の対処では
  ない**([不備の後始末規約](../../docs/guidance/defect-followthrough.md))。原因まで到達したなら、その原因が
  既知の未解決事項として記録されている項目と同じものかを突き合わせ、結果を記録へ反映したうえで、
  直す・打ち切ると決めて理由を残す・ユーザーに諮る のいずれかで終わらせる。自分の道具が困らなく
  なったことは、突き合わせを省く理由にならない。
- **spawn / 再 import 型の子プロセスを使う処理のスクラッチ実行は、その言語・ランナーで必要な
  エントリポイントガードを必ず置く**(Python なら `if __name__ == "__main__":`)。ガード無しはワーカが
  モジュールを再 import して暴走する(逐次経路では露見しないので油断しない)。

## 性能計測

- **指標と目的を一致させる。** 速度を評価するなら wall time(補助に呼び出し回数等)、削減を評価するなら
  サイズ/件数。速度対策の効果を件数で測る等、指標と目的を取り違えない。
- **前後を同一条件で比較する。** 評価したい1変数だけ動かし他は固定する。決定済みの前提どうしを比較しない。
- **ノイズは反復で潰す。** 同一プロセス内で対策を env / 変数でトグルし、ON/OFF を交互に複数回(目安3回)、
  **平均・最小・符号一致**を見る。単発の差(±数%)で判断しない。env トグルなら spawn ワーカも import 時に
  同じ値を読むので一貫する。ベースラインは対策 OFF の安定状態で取る。
- **タイムボックスする。** 単発計測は5分が目安(長くても10分)。重い条件はスライス縮小・対象を絞る。
  上限到達時の打ち切りは、外側ランナーの timeout に頼らずコマンド自身の中で行う。
- **1対策ごとに前後計測し、速くならなければ却下する。** borderline・副作用大なら Codex に諮る。

## 判断

- **着手前に「誰が・どの操作で・どう困るか」を一文で言う。** 言えないなら測らず実装せず、打ち切ると
  決めて理由を残す。未解決事項・残課題の一覧に載っていることは着手してよい理由にならない
  ([困りごとを一文で言えないなら着手しない](../../docs/guidance/work-justification.md#2-困りごとを一文で言えないなら着手しない))。
  ユーザーが名指しで依頼した作業はこの判断の対象外で、疑いがあっても述べたうえで依頼どおり進める。
- **原因を裏取りしてから対策を書く。** 見当をつけただけの原因で実装を始めない。定義・仕様から
  導出で確定できる原因はその導出でよく、導出で
  確定できないものを測る。どちらの裏取りも用意できないなら、実装ではなく判断へ進む
  ([原因を裏取りしてから対策を書く](../../docs/guidance/work-justification.md#3-原因を裏取りしてから対策を書く))。
- **計測が無効に終わったら、手段を作り直す前に価値を問い直す。** 問うべきは「どう測るか」ではなく
  「そもそも測る価値があるか」で、費やした手間は続ける理由にならない
  ([空振りしたら手段でなく価値を問い直す](../../docs/guidance/work-justification.md#4-空振りしたら手段でなく価値を問い直す))。
- **未検証の効果を断言しない。** 期待だけで「〜になっているはず」と言わず、実測・実視聴で確認するまで保留する。
- **成果物へ書く数値は、出所を言えるものだけにする。** 実測値・導出値・引用値・見積りのどれかを
  自分の中で確定してから書き、成果物へ残してよいのは実測値・導出値と、出典を成果物へ併記した引用値とする
  ([数値の根拠規約](../../docs/rules/numeric-evidence.md))。**見積りは、見積りと明記しても成果物に残せない**
  ——裏取りするか、その数値を落とす。**定義・仕様から一意に決まる数値は導出で確定させ、測り直さない。
  実装に依存する量でも、その実装が定める全項と式を示せるなら導出でよい。** 全項を挙げ切れない量
  ——処理系の内部表現・確保の粒度・実行時の回収の挙動が絡み、実装の仕様まで読んでも項が閉じない量
  ——を判断の根拠にするなら、確定させる前に測る。その計算値が実測値に近かったことは確定だったことを
  示さない。
- **「実行しないと確かめられない」という確認結果は、裏取りの要求として扱う。** レビュー・確認の相手が
  裏取りの限界を述べたら、要修正でないという意味ではなく、まだ誰も裏取りしていないという報告である。
  導出を示すか測るかし、どちらもできないならその数値を成果物から落とす
  ([検証範囲の限界の表明は裏取りの要求である](../../docs/guidance/verdict-handling.md#7-検証範囲の限界の表明は裏取りの要求である))。
- **証明できる性質は証明する。** 代表サンプルの結果(N 件で 0% 等)は反例の不在を保証しない。
  一般則として示せるものは、サンプルで済ませず証明する。

## 既知の失敗チェックリスト(着手前に1回なぞる)

| 規律 | ありがちな失敗の形 |
|---|---|
| 起動コマンド・実行環境を推測しない | 推測の起動形/誤った仮想環境で実行して失敗 |
| spawn はガード必須・編集中に走らせない | ワーカがモジュール再 import で暴走/編集中の走行でベースライン汚染 |
| exit/実体で検証 | 外枠 `exit 0`・背景完了通知を成功と誤認 |
| 生成物は可視の場所へ | 出力を scratchpad/temp に置きユーザーが発見できず |
| 一時スクリプトは `.scratch/` へ | リポジトリ直下や追跡パスに置き誤コミット |
| 指標と目的を一致 | 速度対策の効果を件数(サイズ)で評価 |
| 確定前提どうしを比較しない | 決定済みの値を別案と比べ無意味な差を出す |
| 反復でノイズ除去 | 単発比較で符号が安定せず判断 |
| 上限/ kill はスクリプト内・打ち切り可能な構成 | 計測が時間上限を超えて止まらない/プールがオーファン化して kill 不能 |
| 着手前に困りごとを一文で言う | 一覧に載っていることを理由に着手し、誰も困っていない問題を追う |
| 原因を裏取りしてから対策を書く | 見当だけの原因で実装し、効果が出ず実装ごと差し戻し |
| 空振りしたら価値を問い直す | 無効な計測のあと手段の改良を続け、続ける価値を問わない |
| ユーザーの画面・入力を奪わない | 実操作でデスクトップを占有し、ユーザーの作業を止めて測る |
| 踏んだ不具合を迂回で終わらせない | 対象側の不具合を道具側で避けて先へ進み、原因を既知の未解決事項へ突き合わせない |
| 未検証を断言しない | 効果を実測前に「はず」と断言 |
| 束ねず・出力を握り潰さない | 重い処理を1コマンドに詰めて上限に達し、どこまで進んだか判定できない |
| 「実行中」は観測してから言う | 出力が無いことを実行中と読み、確かめずに「継続中」と報告 |
| 通知を唯一の再開手段にしない | 完了通知だけに賭けて待ち、取りこぼしで待ちが無期限になる |
| 証明できる性質は証明する | 一般則を代表サンプルだけで済ませ反例を見落とす |
| 数値は出所を言えるものだけ書く | 見積りを成果物に残したまま確定させ、後から「計算です」と申告 |
| 確かめられないという表明は裏取りの要求 | 「実行しないと確かめられない」を要修正でないと分類し、裏取りせず先へ進む |
