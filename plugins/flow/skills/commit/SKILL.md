# コミット(エージェント委譲)

トークンを使う作業(diff を読む・コミットメッセージを起草する・コミットする・不正コミット防止
チェック)は `flow:commit-worker` エージェント(ワーカー)に委譲する。**メインモデルはコミットメッセージを
書かない。** ワーカーが従う手順・チェック・規約は
[`flow:commit-worker` エージェント自身の定義](../../agents/commit-worker.md)に組み込まれており、
**メインモデルは本文を再掲しない**(再掲は高コストなメインモデルの出力を毎回浪費するため)。

## 導入契約の確認(最初に行う)

本スキルの実行を開始したら、他の何よりも先に[導入契約の確認スクリプト](../../contract/check_adoption.py)を
絶対パスで実行する。**このスキルファイルから見て `../../contract/check_adoption.py` にある**。

```sh
python3 <check_adoption.py の絶対パス>
```

**非0で終わったら、その出力をそのまま示して停止し、[導入契約](../../docs/adoption.md)へ案内する。**
確認する条項とその内容はスクリプトが持つので、ここには書かない。

## メインモデルの責務

メインモデルが行うのは、リポジトリ全体の文脈が要る2つの判断だけ。

1. **対象範囲の決定**: `git status --short` で状態を確認し、このコミットに含める個別ファイルを決める。
   - コミット対象の変更が無ければ、その旨を報告して終了する(空コミットはしない)。
   - 指定以外に既にステージ済みの変更があれば、混入を避けるためユーザーに知らせ、含める範囲を
     確定してから進める。
2. **起動タイミング(指示ゲート・レビューゲート)**: 本スキルを起動してよいのは、ユーザーから
   コミットの明示的な指示があるとき(`flow:autonomous-dev` のようにユーザーが明示起動したスキルの
   手順に含まれる場合を含む)に限る。**修正・実装の指示やレビューが収束した事実はコミット指示に
   ならない**——指示が無ければ収束を報告して止まる。そのうえで、対象変更が**収束**した後だけ。
   収束の定義・結末の種類(収束/千日手/要ユーザー判断)は
   [flow:review-loop-judgement の終了条件](../review-loop-judgement/SKILL.md#終了条件いずれかで停止) が正。
   反復レビューが flow:codex-review-loop・flow:fable-review-loop・flow:opus-review-loop のいずれであっても
   収束の定義は同一で、受理できる。
   **千日手・要ユーザー判断・未完了(実行中/stall/タイムアウト/失敗/ハング/判定未取得)では
   本スキルを起動しない**(ユーザーに諮る / tooling を直して取り直す)。レビューがハング・無出力で
   完走しないとき、メインモデルの判断や合理化でコミットへ進むこと(=収束 verdict の代替)は禁止。
   語検出による enforcement(不正条件の判定)はワーカーが行うので、メインモデルはここで語検出を
   二重に実施しない。

呼び出し元がコミットメッセージ(件名・本文)を持ち込むのは禁止。渡してよいのは一行の意図ヒントだけで、
それを超える文面も、一行でもそのまま件名として通る一文も、ワーカーが不正条件として検出・停止する。

## 委譲の手順

1. 上記の責務1・2を満たすことを確認する。**収束していなければワーカーを起動せず**、ユーザーに諮るか
   tooling を直す。
2. Agentツールを `subagent_type: "flow:commit-worker"` で起動し、プロンプトに下記「ワーカーへ渡す
   プロンプトの型」を渡す。`flow:commit-worker` エージェントは frontmatter でモデルが固定されて
   いるため、呼び出し側で `model` パラメータを指定する必要はない(他モデルの指定・
   上書きも行わない)。
3. ワーカーの報告からコミットハッシュ・件名・残りの作業ツリー状態を確認し、ユーザーに報告する。
   成功と確認できない報告なら、成功扱いにせずユーザーに知らせる。**「不正コミットの疑い」は
   コミットの前に掛かるゲートなので、この報告が来た時点でコミットは成立していない**——履歴は
   変わっておらず、直せば同じ経路で出し直せる。**コミットが成立していないこの停止を、そのまま
   ユーザーへ上げない**——次の手順で取り直せるかを見分ける。
   **ガードの deny や失敗を避けるために起草したメッセージを削った、形式を規約から外した
   (改行をエスケープ表記に置き換えて1行へ詰めた等)、または起草物と別の文面へ差し替えた旨の報告は
   失敗**として扱い、成功として次へ進めずユーザーに知らせる(この回避はワーカーが禁じられている)。
   `Co-Authored-By` トレーラを省いたコミットも同じく失敗として扱う。
   **コマンドの形を試す目的のコミット(試行コミット)は、成立した時点で失敗**として扱う。
   報告された件名が diff の内容を述べていない間に合わせの文面なら、成功扱いにせずユーザーに知らせる。
4. **コミットが成立しないまま止まったときは、止めた理由が何を指しているかで分岐する**
   ([検査に止められたときの規約](../../docs/guard-rejection.md))。ワーカーの停止条件は
   [不正コミットの条件](../../agents/commit-worker.md#不正コミットの条件いずれか該当で不正)が正本で、
   ここでは分岐に必要な区別だけを述べる。
   - **自分が渡した入力の不備を指しているとき**——ワーカーの起動そのものが失敗した、`git commit` が
     権限システム・分類器にブロックされた、
     [条件1](../../agents/commit-worker.md#条件1-verdict-未提示)(収束したレビューの最終応答原文を
     渡し忘れた)・[条件9](../../agents/commit-worker.md#条件9-呼び出し元がコミットメッセージを指定)・
     [条件11](../../agents/commit-worker.md#条件11-呼び出し元が実行モデル表示名co-authored-by値を指定)——は、
     **入力を直して同じ経路で出し直す。一度止められただけで手番をユーザーへ返さない**
     ([止められた一度はまずやり直す](../../docs/guard-rejection.md#2-止められた一度はまずやり直す))。
     条件1で出し直せるのは、収束したレビューの最終応答が実在してそれを渡し忘れていた場合だけで、
     実在しないなら次の分岐に当たる。
   - **レビューの結末そのものを指しているとき**——収束の不在・未対応の指摘・検証対象の不一致・
     合理化句の混入等——は、**取り直しでは解けない。** 入力を直しても通らず、通そうとすれば結末の
     偽装になる。**コミットの出し直しはどの場合も選べない。** そのうえでどちらへ抜けるかは
     **レビューの結末の種類が決める**。まだ結末が出ていない・差分が変わって結末が古くなっただけなら、
     このスキルを抜けてレビューを収束させる。**千日手・要ユーザー判断で終わっていたなら、その結末の
     定めどおりユーザーに諮る**——結末を再レビューで上書きしない
     ([停止規定は停滞回避の推測に優先する](../../docs/user-directives.md#4-停止規定は停滞回避の推測に優先する))。
   - **ステージ対象がレビュー済みの範囲を超えているとき**
     ([条件6](../../agents/commit-worker.md#条件6-範囲外混入))は、**そのファイルを add の対象から
     外して出し直す**。**レビュー済みファイルのリストの側へ足して通してはならない**——それは
     レビューを経ていない変更を通すことになる。
   - **導入契約が満たされていないとき**
     ([条件12](../../agents/commit-worker.md#条件12-導入契約の検証手順書が無い))は、リポジトリ側の
     不足なので取り直しでは解けない。[導入契約](../../docs/adoption.md)へ案内して止まる。
   - どの分岐でも、**通すために起草済みのコミットメッセージや変更内容を書き換えない**
     ([通すために成果物を変えない](../../docs/guard-rejection.md#4-通すために成果物を変えない))。
     変えてよいのはワーカーへ渡す入力と自分の起動の形だけで、ブロックの理由を確かめないまま
     メッセージ側を変えて通す道を検討することも、ここでいう書き換えに含まれる。
   - 取り直しても解けないと分かったら、発行した形と止められた理由をそのままユーザーに報告して止まる。

## ワーカーへ渡すプロンプトの型

```text
作業ディレクトリ: <リポジトリルートの絶対パス>

ステージ対象ファイル(これだけを add):
- <file1>
- <file2>

反復レビュー(flow:codex-review-loop・flow:fable-review-loop・flow:opus-review-loop のいずれか)の最終応答テキスト(原文・要約でない):
<<<
<verdict を含む原文をそのまま貼る>
>>>

レビュー済みファイルのリスト:
- <file1>
- <file2>

意図ヒント(原則「なし」): <なし。渡す場合は一行>
```

- ステージ対象は個別ファイルの明示リストにする(ディレクトリ、`git add -A`、`git add .` は渡さない)。
- **意図ヒントは原則「なし」で渡す。** 渡してよいのは、**コード差分だけでは分からない修正意図**が
  あるときに限る。ヒントは、ワーカーが diff から起草する代わりにそれを写す誘因になる。差分が変更
  内容を語っているなら、ヒントは起草を助けずに歪めるだけになる。
- **ヒントには変更行為の述語を持たせない。** 書くのは差分から読めない理由だけで、何をしたかは
  書かない。「〜へ改める」「〜を追加した」のように変更行為を述べた一文は、一行でもそのまま件名と
  して通るので、ワーカーが起草済みの件名として弾く。書いた直後に読み返し、件名として通る一文に
  なっていないかを確かめる。
- **弾かれたら、述語だけを落として理由の実質は残す。** 理由まで一緒に削った断片は検査を通るが、
  差分から読めない意図を伝えるというヒントの唯一の目的を果たさない
  ([削って通すのは直したことにならない](../../docs/guard-rejection.md#5-削って通すのは直したことにならない))。
  **ワーカーが受理したことは、ヒントが意図を伝えている証拠ではない**——不正条件が見るのは件名の
  持ち込みだけで、ヒントが意図を伝えているかは見ない
  ([受理は目的を果たした証拠ではない](../../docs/guard-rejection.md#6-受理は目的を果たした証拠ではない))。
- 渡す場合も、作業過程参照(ステップ番号・レビューのラウンド番号・作業時点依存の日付・
  「改修前/改修後/今回」等の相対参照・一時ドキュメントへの参照)を書かない。ヒントの言い回しは
  起草に引き継がれるため、メインモデルはヒントを書く時点で混入させない。
- **上記5フィールド以外を追加しない**(実行モデル表示名を含む)。

## 対象外

`--amend` や rebase など履歴の書き換えを伴う操作はこのスキルの対象外。
メインモデルがユーザーに確認した上で直接行う。
