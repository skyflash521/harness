# 成果物衛生規約

リポジトリに残すすべての成果物に、後から参照できない作業過程の記述・個人情報・環境固有情報・
秘密情報・読み手の理解を変えない記述(自明な内容、コードや外部仕様の書き写し、採らなかった案の
比較検討、WHY など)を混入させないための規約。成果物が備える前提を、既に要求している前提で実現
できないときだけ増やし、リポジトリの要求として明示したものに限ることと、作業過程の産物そのもの
(使い捨てのスクリプト・一時ドキュメント)を追跡下に残さないことも含む。本書は**混入を禁じる対象と、正しい置き換え方の正本**とする。

## 1. 適用範囲

- 対象: コミットして残るすべての成果物 — コード・コメント・docstring・テスト・仕様書・
  コミットメッセージなど、種類を問わない。**追跡下へ置くファイルそのものも対象**。

## 2. 作業過程参照の混入禁止

**後から参照できない作業過程の記述**を成果物に残さない。

**禁止する記述:**

- ステップ番号(「Step 3」など)・レビューのラウンド番号。
- **記述理由を作業時点に依存させる日付**(作業日・レビュー実施日など)。
- 「改修前」「改修後」「今回」などの、作業の時点に依存する相対参照。
- **恒久仕様でない一時ドキュメント**(実装計画書・設計メモ・レビュー記録など、コミット後に
  削除されうるもの)への参照。**その見出し・ステップ名も、採番を伴わなくてもこれに当たる。**
- **後の工程で外す前提の一時的な印**(未実装のテストを無効化する理由文字列など)。

**列挙は例示であって語形の一覧ではない。** 上記の既知の語に当たらないことは適合の根拠にならず、
判定は**その記述の出所が成果物の外(計画書・レビューの会話・作業メモ)にあるか**で行う。

**混入に当たらないもの:**

- 仕様上の期日・データ形式の例・テストの固定日など、作業時点に依存しない日付。

**正しい書き方:** 挙動を自己完結で述べる。基準となる別状態を指さず、その記述だけで意味が通る
ようにする(例: 「None なら全初期値を試す」と書く。「改修前と同一」とは書かない)。

## 3. 個人情報・環境固有情報の混入禁止

**個人を特定しうる情報や作業環境固有の情報**を成果物に残さない(特定の形に限定しない)。
書かれた記述だけでなく、**成果物が備える前提**も本節の対象とする。

**禁止する情報(これらに尽きない):**

- ユーザー名・実名・メールアドレス・ホスト名/マシン名。
- ドライブ文字付きやホームディレクトリを含む実絶対パス、ローカルのディレクトリ構造を晒すパス。
- 秘密情報(API キー・トークンなど)。

**混入に当たらないもの:**

- **リポジトリ相対パス**(`scripts/…` のような、そのリポジトリのルートからの相対パス)や
  `file:line` 参照。本節が定めるのは個人情報・環境固有情報として混入でないことのみで、コードと
  ドキュメントの間で参照してよいかは、リポジトリが層構成の規約を持つ場合その文書が別途定める。

**正しい書き方:** リポジトリ相対パスや汎用のダミー値(`/repo`・`user`・`example.com` など)に
置き換えて自己完結させる。

**前提はリポジトリの要求として明示する:** 成果物は、**そのリポジトリが要求すると明示している前提**
だけを備えた環境で動くこと。**前提を増やすのは、既に要求している前提では実現できないときに限る。**
増やすなら、成果物をそれに依存させる差分と同じ差分で、リポジトリが要求を定めている箇所——導入手順・
依存定義など——へ載せる。**載せる前提と、そのバージョンの範囲は、成果物が実際に必要とするものに
一致させる。**

## 4. 読み手の理解を変えない記述の混入禁止

**コードや文脈から自明なこと、既出の記述が既に保証していることの言い直し、正本が別に
ある内容の転記、説明する対象がその場に無い記述、および WHY**を成果物に残さない。

**適用範囲:** 本節が対象とするのは**文書とコミットメッセージ**である(生成器の出力の類型のみ、
追跡下のファイル全般を対象とする)。コード内のコメント・docstring に何を書いてよいかは、本節より
狭い [code-authoring.md](code-authoring.md) が定める。

**適用の限定:** 下記のうち変更履歴の叙述・外部仕様の転記・採らなかった案の比較検討の3類型は、
**変更そのものを主題としない文書の本文**を対象とする。コミットメッセージ・CHANGELOG・移行手順書など、
変更や検討を記述すること自体が役割である成果物は、この3類型の対象外とする。

**禁止する記述:**

- コードや文脈から自明な内容(例: `.gitignore` 内に「コミットしない」と書く)。
- **その文書が定めないことの、委譲先を示さない宣言**(「〜は定めない」「〜は扱わない」)。どこが
  正本かを示す委譲(「X は〈正本〉が定める」)と、**その文書の判定を変える対象外の明示**は、
  これに当たらない。
- 構造や既出の記述が既に保証していることの言い直し(例: 参照先を「ここを正とする」と
  明示した直後に「ここに重複させない」と付す)。
- **直前の語句を言い換えただけで、外しても意味が落ちない括弧書き**(例: 「どう作業するか(規約)」)。
- 変数名・式・処理内容の逐語的な書き写し(例: 関数の処理を1行ずつ言い換えて並べる)。
- **変更履歴・過去の実装の叙述**(「以前は〜していた」「〜から移行した」と述べる類)。正本は git の
  履歴とコミットメッセージ。
- **ライブラリ・外部 API の仕様の転記**(引数の意味・戻り値・バージョンごとの挙動などの書き写し)。
  正本は当該ライブラリの文書。
- **追跡下の生成器を走らせれば同じ内容が出る成果物。** 正本は生成器とその入力である。追跡下へ置いて
  よいのは、リポジトリが前提とする環境の外に居てその生成器を走らせられない読み手のために置く場合に限る。
- **採らなかった案の比較検討**(検討した代替案とその却下理由の列挙、まだ書いていない対応の予告)。
  検討の過程の置き場は一時ドキュメントとする。**「調べた内容が失われる」ことは、
  それ自体では残す理由にならない**——残すかどうかは、その記述が無いと読み手が現在の挙動を誤るかで
  決まる。
- **WHY**(なぜその設計・規則・手順にしたかの理由づけ)。**語形で判定しない**——削っても到達状態と
  従うべき動作が変わらないならそれが WHY である。**この禁止の対象外になるのは
  [§5](#5-why-を記述することが主たる役割の成果物) が挙げる成果物だけ**で、上の適用の限定は
  本項に掛からない。

**混入に当たらないもの:**

- **非自明な事実**(隠れた制約、不変条件、読み手が驚く挙動、依存先の罠)。到達状態の一部として
  書く。**そこから設計・規則を選んだ筋道を続ければ、続けた部分から先が WHY。**
- **現在の挙動の限界**(何を検出しないか・何を保証しないか)。禁じているのは、その限界に至るまでに
  比較した案の一覧のほうである。
- **利用者向け文書**(その成果物の利用者へ導入と利用を案内することが**主たる役割**である文書。
  規約・仕様・手順の正本はこれに当たらず、案内が主たる役割の文書が一部の事項の正本を兼ねることは
  妨げない)**が置く概要・手順と、対象を並べた一覧。** 利用者が全体を掴み、どれをどう使うか選び、
  導入と利用を進められるようにするための記述は、正本と同じ内容に触れていても転記に当たらない。
  **ただしどの形でも、正本の改訂に連れて変わる内部の設定・条件の列挙は含まない。**
  **この免除は利用者向け文書と、次の `CLAUDE.md/rules` に限る。**
- **`CLAUDE.md/rules`**(種別の定義は[適用範囲](document-authoring.md#1-適用範囲))**が置く、所在に
  添えた役割の説明と、どれが正本かの道しるべ。** 正本と同じ内容に触れてよい。ただし内部の設定・
  条件の列挙を含まないことは、ここでも同じく効き、**その文書自身が
  何のための文書かの説明はこの免除に含まない。**

**正しい書き方:** 書く前に、その記述を消したときに読み手の理解が変わるかを自問する。変わらないなら
書かない。判定は一文単位でなく**段落・節の単位**で行う。ただし残してよい記述が一文でも入っていれば
全体が適合、とはしない——**それを保ったまま削れる叙述・転記・WHY が残っているなら、その部分が
混入**である。説明は、それが説明する対象の隣に置き、離れた場所へ集約しない。

## 5. WHY を記述することが主たる役割の成果物

[§4](#4-読み手の理解を変えない記述の混入禁止) が禁じた WHY を書いてよいのは、**WHY を記述する
ことが主たる役割である成果物**に限る。**コミットメッセージはこれに当たる。** コード内のコメント・
docstring は [code-authoring.md](code-authoring.md) の定めによる。

**役割で判定する。** 規約文書・仕様書・スキル文書・エージェント定義・フックが注入する文脈と
deny 理由・`CLAUDE.md/rules`・利用者向け文書は当たらない。**読み手がエージェントでも同じ**で、
理由が無いと動けない・当てはめが決まらない・別の行動へ逸れるなら、書き足すのは WHY ではなく指示。

## 6. 作業過程の産物を追跡下に残さない

使い捨ての計測・検証スクリプトと、恒久仕様でない一時ドキュメント
は[スクラッチ置き場](adoption.md#2-スクラッチ置き場)に置く。**リポジトリの追跡下へ置かない。**
