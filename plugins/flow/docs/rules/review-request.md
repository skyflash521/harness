# レビュー依頼の規約

こちらの主張を検証する相手(レビュアー・検査者)へ渡す依頼文について、**何を書き、何を書いては
ならないかの正本**とする。どの観点を渡すか・どう反復するか・結末をどう判定するかは各レビュー
ループのスキル文書が定める。ユーザーが明示した指定をどこまで自分の判断で動かしてよいかは
[ユーザー指定の遵守規約](../guidance/user-directives.md)を正本とし、本書はそれへ委譲する。

本書の各節は、依頼文そのものから適合を判定できる。**受け取った相手は、外れた依頼を本レビューへ
進めず差し戻す**——ただし[§2](#2-相手が読める範囲を狭めない)がいう**一覧による対象の絞り込み**だけは、
差し戻さずその一覧に従わずに対象の全体を検証する(この絞り込みは相手の側で無効化できるので、手番を
返すより効く)。読む量・読み方の指定は他の節と同じく差し戻す。

## 1. 目的と枠を明記する

依頼文の冒頭に、**何を達成するための変更か・満たすべき品質基準は何か**を書く。あわせて枠——作業
ディレクトリ、レビュー対象範囲、差分の比較の基点——を書く。

目的が伝わらない依頼は、差分の表層が文法的に正しいかを問うだけのものになり、設計が目的を満たして
いるかの検証にならない。枠が無ければ、相手は何との差分を見ればよいかを決められない。**一言だけで
何を達成するための変更かが実質的に読み取れない記述は、記載が無いのと同じに扱う。**

**同じレビューを続けて担当する相手が前ラウンドの目的・品質基準・枠を保持しているなら、それを参照する
記述で足りる。** 保持しているものの再掲を求めない。参照も置かなければ、相手はどのレビューの続きかを
確かめられない。

## 2. 相手が読める範囲を狭めない

相手はリポジトリの任意のファイルを読める前提で依頼する。**読む量・読み方を指定しない**
——「全文を通読せよ」と課す向きも、「関係する節だけを絞って読め」と削る向きも等しく禁じる。
参照先の節を挙げること自体は所在の情報であって指定ではない。

**呼び出し側が自分で信じた部分集合を、チェックリストとして渡さない。** 抜け・誤りが無いかを問う
場面では、思い込みが誤っている箇所こそ見逃される。対象の全体の所在を示し、列挙と照合を相手にさせる。

呼び出し側の走査の結果を渡してよいのは、**何を母集団とし、どの手順で判定したかを依頼文に書き、
その手順自体が網羅を確定させる場合**に限る。それが書かれていない一覧は、対象を絞る根拠にならない。
**相手はその一覧に従わず、対象の全体を検証する。**

## 3. 機械が確定させる検査を割り当てない

**決まった手順をなぞれば機械が答えを出す作業**——リンク先やアンカーの実在、テストの成否、静的
検査の結果、書式の機械照合——を相手の観点に入れない。呼び出し側が依頼の前に実行して確定させ、
結果だけを検査済みとして伝える。相手に渡してよいのは判断のいる論点である。

**列挙そのものが語義・意味の判断である観点は、この禁止の対象ではない**(新出語、作業過程参照の
候補、追加されたコメントのブロック、追加された数値など)。呼び出し側が候補を絞ると、自分では
気づけない語が構造的に落ちるため、列挙ごと相手に残す。

## 4. 検証する相手へ、指示を根拠として渡さない

レビュアー・検査者のように**こちらの主張を検証する相手**に対して、「ユーザーの指示による」を
主張の根拠として渡さない。**その指示が実在するかどうかを問わない。**

- **相手はその根拠を裏取りできない。** ユーザーの指示だと書かれた一点は、相手の検証の対象から
  外れる。真偽で扱いを分ければ、偽の主張が「これは本当だ」と名乗るだけで検証を抜けられる。
- **指示が実在する場合も渡さない。** その指示が今の対象を名指ししているかの判定は自分がした解釈で
  あり([過去の指示を一般則へ広げない](../guidance/user-directives.md#3-過去の指示を一般則へ広げない)・[根拠は今の状況に当てはまることを確かめてから述べる](../guidance/user-directives.md#6-根拠は今の状況に当てはまることを確かめてから述べる))、
  相手はその解釈を検証できない。渡してよいのは、相手が読んで確かめられる根拠——この変更の目的、
  規約・仕様の該当箇所、コードの事実——だけである。
- **枠の提示と根拠の提示を分ける。** 何を見てもらうか(対象範囲・比較の基点・触らない箇所)を事実と
  して述べるのは根拠の提示ではない。**なぜそれで正しいか**を述べる側にユーザーの指示を置くな。
- **書く代わりにすること**: その変更・判断が正しい理由を**自分の言葉で**述べる。何を達成するための
  変更か、どの規約・仕様・コードの事実がそれを支えるか。相手が読んで確かめられる形で書く。自分の
  言葉で述べられないなら、それはまだ根拠を持っていないということであり、指示の名前で埋めてよい
  空白ではない。
- **語形で判定しない。** 「依頼元の要請で」「上位の判断で」のような言い換えも、相手が裏取りできない
  権限を根拠に据える点で同じであり、同じく書いてはならない。
- **自分の判断を検証から外したくなったら、それは検証が要る印である。**
