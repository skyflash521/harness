# コード内コメント規約

コード内のコメントと docstring について、**書いてよい場合と、書かずに済ませるときの移し先の正本**と
する。何を成果物に混入させないか(作業過程参照・個人情報・環境固有情報・読み手の理解を変えない記述)は
[artifact-hygiene.md](artifact-hygiene.md)、コードとドキュメントの主従および文書種別ごとの記述範囲・
粒度は [document-authoring.md](document-authoring.md) を正本とし、本書はそれらへ委譲する。

## 1. 適用範囲

- 対象: コミットして残るコード内のコメントと docstring(`#`・`//`・`/* */` など)。設定ファイルの
  コメントを含む。
- 対象外: 文書・コミットメッセージ。
- 本書が閉じるのはコメントという媒体だけである。**コメントで禁じたことは、リポジトリで禁じたことでは
  ない**——[§3](#3-例外に当たらない記述の行き先)のとおり、多くは名前・型・テスト・恒久仕様書の
  いずれかへ移る。

## 2. 原則と4つの例外

コード内のコメントは**原則として書かない**。「消しても理解が変わらないか」で個別に判定する形は、判定が
書き手自身の主観に委ねられ、説明を足す側へ倒れる。本書は媒体そのものを既定で閉じ、**下記の4類型だけを
例外として許す**。例外に当たらない記述は、
内容の正しさを問わず書かない——**その情報の置き場はコメントではなく、名前・型・テスト・恒久仕様書の
いずれかである。**

1つのブロックが複数の例外にまたがることはある(bash スクリプトの冒頭は概要と呼び出し契約を同時に
持つ)。その場合は当たる例外をすべて名指しし、**どの例外にも当たらない部分は削る**。

### 例外1: 機械が読むもの

実行・検査・生成の入力になり、**消すとそのいずれかが壊れる**もの。shebang、リンタの抑制指示、検査
スクリプトが grep する固定マーカーなどが当たる。判定基準は「消すと壊れるか」であって、慣習でも
見た目でもない。

### 例外2: リポジトリ外の事実

OS・外部ツール・外部製品・言語処理系の仕様のうち、**そのリポジトリを全部読んでも分からない**もの。
「既定の符号化で読むと非ASCIIが化け、フックが無言で違反を通す」「git はパスを UTF-8 バイトで出す」
「CRLF でチェックアウトすると shebang が壊れる」などが当たる。

- **リポジトリ内で完結する理由は書かない。** 他の規約・他の分岐・先に走る規則・過去の経緯は、その正本が
  別にある。コメントへ写さず、正本が無いならコメントではなく正本を作る(コードから文書への参照を
  張ってよいかは、リポジトリが層構成の規約を持つ場合その文書が定める)。
- **1件1行**で、その事実が効いている行の隣に置く。段落にしない。ただしその事実がファイル全体の存在
  理由そのものである場合は、[例外4](#例外4-コード冒頭の概要)の概要に含めてよい。

**不作為の説明(なぜ入れていないか)は独立した例外ではない。** 何を入れていないかという事実はテストが
固定し、コメントに残せるのは、その理由が本例外に当たるときの1行だけである。失敗方針(fail-open か
fail-closed か)も同じで、呼び出し側の扱いが変わるなら[例外3](#例外3-呼び出し契約)・[例外4](#例外4-コード冒頭の概要)の
契約として書き、変わらないならテストが固定する。

### 例外3: 呼び出し契約

呼び出し側が知らなければ正しく呼べない契約——終了コードの意味、標準出力の書式、前提条件。
**その契約を言語の機構(型注釈・docstring など)で表せるなら、コメントではなくそこへ書く。**
コメントに残せるのは、機構では表せない契約だけである。

### 例外4: コード冒頭の概要

ファイルの冒頭と、関数・クラスの冒頭に置く概要。docstring 機構がある言語ではそれを使う。書けるのは
**そのコードが何のために在るか、外から見て何を引き受けるか**までである。

**挙動の詳細をそのまま自然言語へ写さない。** 処理の順序、分岐の条件、繰り返し、呼んでいる API の
名前、リテラル値の言い換えは書かない。

**判定:** その記述を残したまま**実装を丸ごと書き換えられるか**を見る。書き直しが要るなら、それは挙動の
詳細であって概要ではない。

- 概要として書ける: 「ドライブルート起点の再帰探索を deny し、走査対象がリポジトリに絞られる代替へ誘導する」
- 詳細なので書けない: 「コマンドをセグメントに分け、各セグメントの先頭語が走査コマンドかを見て、その
  パスオペランドがルート相当かを判定する」

## 3. 例外に当たらない記述の行き先

| 書きたくなった内容 | 置き場 |
|---|---|
| テストのケースが何を固定しているか | ケースに持たせる名前。**失敗時の出力に現れること**を条件とする |
| 定数・変数・関数が何を表すか | 名前 |
| 値の並びや組み合わせの意味 | 型(namedtuple・dataclass など) |
| 不変条件・境界・並び順への依存 | それを破ったときに落ちるテスト |

**表に無い記述は、恒久仕様書が扱う範囲なら恒久仕様書へ移し、そうでなければ消す。** 移し先が
見つからないことは、コメントに残してよい理由にならない。

**コメントで補わないと読めないコードは、コメントが足りないのではなく、名前・型・テストが足りない。**
コメントを足す前に、そのどれが足りていないのかを先に見る。
