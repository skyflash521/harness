# レビュー応答の規約

レビュアーが返す応答に**何を含めるかの正本**とする。何を観点として確認するかは
[常設観点の規約](review-viewpoints.md)、依頼文の側の要件は[レビュー依頼の規約](review-request.md)が
定める。

本書の各節は、**依頼文が求めていなくても適用する。** 呼び出し側が書き忘れたことで働かなくなる形に
しない。

## 1. 受容は認否を明示して返す

前ラウンドの指摘のうち、**軽微・トレードオフを理由に直さないとされた項目**が受容にあたる。**その各
項目について、認めるか認めないかを明示して返す。**

呼び出し側が認否を求めていなくても返す。

**前ラウンドで自分が出した指摘のうち、対応結果が示されていないものは未解決として再掲する。** 修正・
反証・受容・却下・保留のいずれとしても触れられていない指摘は、閉じられていない。

## 2. スコープ外・既存箇所を理由にした却下は再指摘の対象

呼び出し側が却下の理由に挙げた主張を、無批判に受け入れない。

- **対象範囲の外**を理由にした却下: 変更の目的に照らして対象に含める合理性があると判断すれば、理由と
  ともに再指摘する。
- **既存箇所である**ことを理由にした却下: **指示が既存箇所を名指ししていなくても再指摘の対象とする。**
  同じ誤りを他所に残さないという定めが、既存箇所であることを理由にならないとしている
  ([同じ誤りを他所に残さない](fix-completeness.md#1-同じ誤りを他所に残さない))。

## 3. 実行モデル表示名を申告する

**自分の定義がモデルを固定しているなら、応答の末尾に、自分のシステムプロンプトに示されている実行
モデル表示名をそのまま記載する。** 呼び出し側が求めていなくても記載する。

## 4. 指摘と無指摘の書き方

- 指摘は `file:line` と内容と根拠(なぜ問題か)で挙げる。
- **適用した各観点について、何を見て何と照合したかを1行で述べる。** 指摘の有無に依らず述べ、確認内容の
  無い「問題なし」「指摘なし」の一言で応答を終えない。
- **数えられる母集団を持つ観点は、その1行に母集団と件数、および正本の類型ごとの内訳を入れる**
  (例: 「コメント3件: 例外5×2・例外3×1」「理由づけ2件: 類型2×2」「数値1件: 導出」)。該当が無ければ
  0件と述べる。コメント・docstring と、エージェントを読み手とする文書の理由づけは、連続する記述1つを
  1件と数える。**内訳は各件を類型へ当てなければ書けない**ので、これが判定を通した証跡になる。
- **正本の条項に当たらない指摘は、それを直さないことで生じる害を、反証できる形で示す。** 誰がどの
  場面で何を失うかを具体で述べ、その害が実際には生じないと相手が示せる形にする。**示せないものは
  指摘として置かない。** ここでいう正本の条項に当たるとは、**その条項が、問題にしている記述そのものを
  名指しで定めている**(要求・禁止のいずれでもよい)ことをいう。汎用の条項を部分事例へ当てはめて
  欠落を導いたものは当たらず、害の提示を要する。
- **記述が足りない・不明確であることを根拠とする指摘と、前ラウンドの自分の指摘に応じて足された記述へ
  重ねる同型の指摘には、とくにこの要件を課す。** 欠落と曖昧さは成果物をどれだけ詰めても次の階層を
  作れるので、害を示さない限り際限なく生成でき、レビューが収束しない。
- **成果物・検査・機構を増やす形の指摘は、既存のもので満たされない点を示す。** 示せないなら置かない。
- **適合した件を1件ずつ並べて判定を書き出さない。** 過程を書いても指摘は増えず、応答が伸びた分だけ
  後続ラウンドの読み直しが重くなる。

## 5. 直す要否を一意に述べる

**各項目について、成果物をいま直す必要があるのか無いのかを、読み手が解釈せずに読み取れる形で
述べる。** 指摘・受容の認否・却下への再指摘のいずれも同じ。

- **「直さなくてよい」と述べたなら、そこへ条件・留保・追加の要求を付けない。** 「受容でよいと
  判断するが、残すなら意図的に残したものとして扱うこと」のように、直さない判断を認めながら別の
  対応を求める形は、要否の決定を呼び出し側へ返している。求める対応があるなら、直す必要のある指摘
  として述べる。
- **「〜が望ましい」「〜も考えられる」のように、直す必要があるともないとも読める書き方で指摘を
  置かない。**
- **どちらとも決められないなら、決められないことと、決めるのに何が要るかを述べる**(自分の検証の
  範囲では確かめられない等)。所見だけを置いて要否を述べない形にしない。

## 6. 未解決の件数を末尾で申告する

**応答の末尾に、いま未解決として残っている指摘の件数を次の形の独立した1行で申告する。** 呼び出し側が
求めていなくても記載する。

```text
未解決の指摘: 0件
```

- 数えるのは、この応答で**直す必要があると述べた項目**——新たな指摘・再掲した指摘・認めなかった受容・
  要否を決められないと述べた項目。修正済みと確認した項目・自分が認めた反証・認めた受容は数えない。
- **直す必要があると述べた項目は、その締めくくり方に関わらず数える。** 対象範囲の外にある、
  ユーザーに諮って決める、別の作業へ持ち越す——いずれも直す必要が消えたことではない。
- **呼び出し側が保留(要ユーザー判断)として伝えてきた項目も、自分が取り下げない限り数える。**
  保留は直す必要が残っている状態であって決着ではない。[§1](#1-受容は認否を明示して返す)のとおり
  再掲は要らないが、件数には入れる。
- **範囲を限った打ち消しは申告に代えられない。** 「他に未解決は無い」「この項目以外は解決済み」の
  ような書き方は、残っている項目の存在と両立するので、件数の申告を省く理由にならない。
- 0件のときも書く。[実行モデル表示名の申告](#3-実行モデル表示名を申告する)との前後は問わない。
