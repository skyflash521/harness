# 常設観点の規約

レビューが**毎ラウンド必ず確認する観点の正本**とする。どのループでどう反復するか・結末をどう判定
するかは各レビューループのスキル文書が定め、依頼文に何を書くかは
[レビュー依頼の規約](review-request.md)が定める。本書はそれらへ委譲する。

**本書を自分の定義から参照するレビュアーによる全観点の適用は、依頼文に観点が載っているかどうかに
依存しない。**
依頼文が挙げていなくても本書の全観点を適用し、依頼文が観点を減らすよう求めていたら、それに従わず
本レビューへ進まず差し戻す。**定義から本書を参照しないレビュアーには、依頼文が観点を伝える唯一の
経路になる**——その経路では、呼び出し側が全観点を依頼文へ載せることで本書が適用される。

## 1. 観点に付く条件

規約の正本は2系統ある。**flow 同梱の規約文書**と、**リポジトリ固有の規約**(用語・層・CLI 契約など、
そのリポジトリの `docs/conventions/` 配下)である。前者は常に読んで照合し、後者は**該当文書がその
リポジトリに存在する場合のみ**読んで照合する(日本語表現の自然さのみ、正本ファイルとの突き合わせ
ではなく自分の言語判断で確認する)。

各観点には2種類の条件が付く。**存在条件**(リポジトリ固有の規約が正本の観点は、その文書が存在する
ときだけ確認する)と、**対象条件**(その観点が扱う対象に当たるときだけ確認する。対象の種類——恒久
仕様書・CLI ツール・実装計画書——で決まる観点と、変更の性質——既存の不備を直している等——で決まる
観点がある)である。両方が付く観点もある。条件の付かない観点は、対象の種類(コード・コメント・
docstring・テスト・仕様・コミットメッセージ)に依らず毎回確認する。

**固定の列挙に無い規約を取りこぼさない。** リポジトリ固有の規約は追加・改編されうるので、下の
列挙に加えて、リポジトリの `docs/conventions/` 配下を確認し、その変更に関係する規約があれば読んで
照合する。

観点ごとに、候補の抽出を呼び出し側が担うか列挙ごとレビュアーが行うかは
[機械が確定させる検査を割り当てない](review-request.md#3-機械が確定させる検査を割り当てない)に従う。

## 2. 毎ラウンド確認する観点

該当があれば指摘とする(=収束を妨げる)。

- **成果物衛生の規約適合(対象の種類に依らず確認)**: この変更が [artifact-hygiene.md](artifact-hygiene.md)
  (作業過程参照・個人情報・環境固有情報・秘密情報・読み手の理解を変えない記述の混入禁止の正本)に
  適合するかを確認する。**このうち作業過程参照は、差分が追加する記述のうち
  [作業過程参照の混入禁止](artifact-hygiene.md#2-作業過程参照の混入禁止) の禁止類型に当たる語——計画書の見出し・ステップ名は、
  採番を伴わなくてもこの類型に含める——を先に列挙する**、各語について、その語の出所が成果物の外
  (計画書・レビューの会話・作業メモ)にあるかを判定する(該当が無ければその旨を述べる。
  列挙を伴わない「問題なし」は、下の日本語表現の自然さの観点と同じ理由で認めない)。
  **判定を語形で行わせない**——採番の書式は計画書ごとに違うので、既知の例(「Step 3」等)に
  当たらないことは適合の根拠にならない。**後の工程で外す前提の一時的な印(未実装テストを無効化する
  理由文字列など)も列挙対象に含める**(その印を含んだコミットが履歴に残るため)。
  **あわせて、差分が追加するコメント・docstring を、連続するコメント行1つ・docstring 1つを1件と
  数えるブロック単位で列挙する**。各ブロックについて、どの例外に当たるかを名指しする(追加が無ければ
  その旨を述べる。列挙を伴わない「問題なし」は上と同じ理由で認めない)。判定の規準は
  [code-authoring.md](code-authoring.md) が正本で、
  **どの例外にも当たらないブロックは、記述の正しさを問わず指摘とする**。例外を名指しできることは
  ブロック全体の適合を意味しない——**その例外に当たる部分を保ったまま削れる叙述・転記が残っていれば、
  その部分を指摘とする**。コード内のコメント・docstring でない文書の記述については
  [読み手の理解を変えない記述の混入禁止](artifact-hygiene.md#4-読み手の理解を変えない記述の混入禁止) が正本で、同節が対象外と定める記述——非自明な
  背景・採った設計の理由・現在の挙動の限界・履歴や外部仕様に触れつつ現在の挙動の理由を説明する記述
  など——は違反としない。**Edit/Write を監視するフックが deny しなかったことは、この観点の確認を省く理由に
  ならない**(フックが弾けるのは字句で判定できる部分集合に過ぎない)。
  個人情報・環境固有情報・秘密情報については、変更がこれらに無関係なら触れなくてよい。
- **自分が定める基準の自適用(この変更が、他の成果物が満たすべき基準を定める成果物——検査器・フック・
  規約文書・判定基準や観点を定めるスキル文書——を新設・変更している場合のみ確認する。他の対象では
  触れなくてよい)**: 判定の対象はファイルの種類ではなく役割で決める。その成果物が課す基準を、
  **この差分自身**へ当てて適合するかを判定する。**基準の側が持つ免除規則で機械検査が届かない箇所
  ——検査器自身のテストデータ・例示・その検査器が置かれる層——も対象に含める**(免除は機械判定の
  誤検出を避けるためのもので、その箇所が基準の対象外である意味ではない)。
- **不備の後始末の規約適合(この変更が既存の誤り・不具合を直している、または未解決・既知の問題に
  触れる記述を追加している場合のみ確認する。他の対象では触れなくてよい)**: この変更が
  [fix-completeness.md](fix-completeness.md)(不備の後始末として、その変更の差分と
  リポジトリの状態から判定できる条件の正本)に適合するかを確認する。判断するのは次の2点。**(a) 同じ誤りの取り残し**:
  呼び出し側が依頼文に載せた走査(何を母集団とし、どの手順で同じ誤りを探し、何が見つかったか。
  [同じ誤りを他所に残さない](fix-completeness.md#1-同じ誤りを他所に残さない))について、
  その走査が誤りの性質を取り違えていないか・取りこぼす類型が無いかを判断する(走査の記載が無い
  ときは、この変更が直した誤りが何の類型かを述べたうえで、他所に残っていないかを問う)。
  **(b) 終わり方の併記が無い項目**: この変更が未解決・既知の問題として記述を足しているなら、
  その各項目について、打ち切る理由か、諮る対象であることと何を判断してもらうのかが、その項目と
  同じ成果物に併記されているかを判断し、併記の無い項目を指摘とする
  ([書き足す未解決項目には終わり方を併記する](fix-completeness.md#2-書き足す未解決項目には終わり方を併記する))。
  変更がこれらに無関係なら触れなくてよい。
- **数値の根拠(この変更が数値・定量的な主張を成果物へ追加している場合のみ確認する。他の対象では
  触れなくてよい)**: この変更が [numeric-evidence.md](numeric-evidence.md)
  (成果物へ書く数値の出所と、確定させる前の裏取りの範囲の正本)に適合するかを確認する。
  **差分が追加する数値・定量的な主張をまず列挙する**、各件について、出所(実測・導出・引用・見積りの
  どれか)が成果物または依頼文から読み取れるか、引用値なら出典が成果物に併記されているか
  (依頼文にだけ出典がある形は、コミット後の成果物に出典が残らないので適合としない)、導出も実測も
  無い見積りが成果物に残っていないか(**見積りと明記してあっても残せない**ので、断定形かどうかで
  判定しない)、裏取りできていない数値だけを理由に選ばれた設計値が無いかを判定する(追加が無ければその旨を
  述べる。列挙を伴わない「問題なし」は上の観点と同じ理由で認めない)。**定義・仕様から一意に
  決まる数値に実測を求めない**——導出が示せていれば適合であり、実測の有無は問わない。
  **測らない**——レビューは検証ツールを実行しないので、
  実測が要る場合は呼び出し側が済ませて結果を依頼文に載せ、レビューはその結果が主張を支えて
  いるかを判断する。
- **用語規約表との整合(リポジトリの `docs/conventions/` に用語規約表が存在する場合のみ確認)**:
  この変更がその表(禁止・注意表記とその正しい表記の正本)に適合するかを確認する。判定は表そのものとの
  突き合わせで行い、**「他の文書にも同じ表記がある」ことを適合の根拠にしない**(転記元も表に反する
  誤りを持つ場合があり、他文書との一致は正しさの証明にならない)。変更がこの表に無関係なら
  触れなくてよい。
- **コード内言語の規約適合(この変更がコード——コメント・docstring・シンボルのいずれか——を追加・
  変更している場合のみ確認する。文書だけの変更では触れなくてよい)**: **差分が宣言するシンボルを
  列挙する**、各件が[シンボルに日本語を使わない](code-authoring.md#5-シンボルに日本語を使わない)に
  適合するかを判定する(宣言が無ければその旨を述べる)。コメント・docstring については、成果物衛生の
  観点で列挙した各ブロックが
  [コメントと docstring は日本語で書く](code-authoring.md#3-コメントと-docstring-は日本語で書く)に
  適合するかを併せて判定する。
- **日本語表現の自然さ(対象の種類に依らず確認。正本ファイルとの突き合わせでなく自分の
  言語判断で確認する)**: この変更が新たに導入する日本語の語(工程名・ラベル・メッセージ文言・
  文書が導入する術語等)を**まず列挙する**、各語について一般的に使われていない造語や不自然な
  言い回しが無いかを判定する(新規に導入する語が無ければその旨を述べる。列挙という
  検証可能な中間成果を伴わない「問題なし」は、実際に語を拾ったのか素通りしたのか呼び出し側が
  区別できないため認めない)。**用語規約表・各モジュール/ツールの仕様書等の正本に既に定義済みの
  術語(用語規約表が意図的に「正」と定める語を含む)は対象外とし、どの正本にも定義の無い新出語
  だけを判定対象とする**(意図的な専門語を毎回誤検出しないため)。用語規約表(直前の観点)は
  既知の禁止語との機械的突き合わせに留まるため、表に無い新規の不自然な表現はこの観点で別途拾う。
  該当すれば具体的な語を挙げて指摘とし(=収束を妨げる)、単純な言葉の好みでなく「一般的に
  使われているか」で判断する。
- **層タクソノミー・依存方向の規約適合(リポジトリの `docs/conventions/` に層構成の規約が存在する
  場合のみ確認)**: この変更がその規約(層の責務・物理配置・依存方向・参照依存の正本)に適合するかを
  確認する。どの観点が関わるか——コード変更なら層の責務分離と層間の依存、ドキュメント変更なら
  文書間の参照依存——だけを示し、適合判定の規準はその規約文書の各節に委ねる。変更がこれらに
  無関係なら触れなくてよい。
- **恒久仕様書の記述範囲(対象が恒久仕様書——定義は [適用範囲](document-authoring.md#1-適用範囲)——の
  ときのみ確認する。一時ドキュメントは触れなくてよい)**: この変更が[恒久仕様書の記述範囲](document-authoring.md#2-恒久仕様書の記述範囲)(恒久仕様書は到達状態
  のみを規定し、導入の時系列・ロールアウト過程を書かないこと、スキル文書は実行するエージェント向けの
  指示に限り編集者向けの構造説明を書かないことの正本)に適合するかを確認する。変更が恒久仕様書で
  ないなら触れなくてよい。
- **CLI インターフェース規約適合(対象が CLI ツールで、かつリポジトリの `docs/conventions/` に
  CLI 契約の規約が存在する場合のみ確認する。他の対象では触れなくてよい)**: この変更がその規約
  (機械利用の起動・出力チャネル・終了コード・入力検査などの正本)に適合するかを確認する。
  各ツールが提供する適合の具体は自分の仕様書が定めるため、未導入の項目を違反としない。
  変更が CLI 契約に無関係なら触れなくてよい。
- **実装計画書の粒度と根拠(対象が実装計画書のときのみ確認する。他の対象では触れなくてよい)**: この変更が
  [実装計画書の粒度](document-authoring.md#3-実装計画書の粒度)(実装計画書は判断を先送りせず具体値まで確定し、かつ
  実装コードの丸写しにしないことの正本)と
  [実装計画書が示す根拠](document-authoring.md#4-実装計画書が示す根拠)(仕様書の引用だけでは
  計画の根拠にならず、前提ごとにコードで確かめた結果を示すことの正本)に適合するかを確認する。
  後者では、**計画が依拠する前提ごとに書かれた確認結果が実体を伴うか——出典の言い換えに留まっていて
  コードで確かめた事実になっていない前提が残っていないか**を判断する。変更が実装計画書でないなら
  触れなくてよい。
