# 検査に止められたときの規約

自分が出した入力・コマンド・成果物が検査に止められたとき、**次に何をしてよいかの正本**とする。
どの検査が何を弾くかは定めない(各フック・各エージェント・各スキルの定義が正本)。原因をどこまで
裏取りすれば対策を書いてよいかは[着手判断規約](work-initiation.md)、止まった項目をどう終わらせるか
は[不備の後始末規約](../rules/defect-followthrough.md)、ユーザーが明示した指定をどこまで動かしてよいかは
[ユーザー指定の遵守規約](user-directives.md)を正本とし、本書はそれらへ委譲する。

## 1. 適用範囲

**自分の側の入力を直せば通りうる停止**を対象とする。フックの deny、権限システム・分類器による
ブロック、委譲先エージェントが呼び出し側の入力の不備を理由に返した停止、検査器・CI の不合格が
該当する。

**対象外は、状態がゲートの条件を満たしていないことを告げる停止**である。レビューが収束していない、
承認がまだ無い、といった停止は入力の不備の報告ではなく状態の報告であり、入力を直しても通らない。
スキルが定める停止規定が発火した停止も同じく対象外で、止まって諮るのが正しい終わり方である
([停止規定は停滞回避の推測に優先する](user-directives.md#4-停止規定は停滞回避の推測に優先する))。
**分類を決めるのは、停止規定が在るかどうかではなく、止めた理由が何を指しているかである。**
委譲先が停止規定に従って止まった場合でも、その理由が呼び出し側の入力の不備を指しているなら本書の
対象で、状態・結末を指しているなら対象外になる。

**個別の停止条件をどちらに振り分けるかを各スキルが列挙しているなら、その列挙が正本**で、本節の
定義は列挙の無い停止に当てる。**どちらか曖昧なら対象外に倒す**——やり直しに回せる停止を諮ったときの
損は手番1回だが、逆向きの誤りはゲートを通すための試行になる。

## 2. 止められた一度はまずやり直す

**一度止められただけの停止は、それ自体ではユーザーの判断を要する事象ではない。** 原因を切り分けた
うえで取り直し、**取り直しても解けないと分かってから諮る**。

- **別経路で代行しないことは、同じ経路でやり直さない理由にならない。** ブロックされた操作を別の
  手段で通さないという禁止が禁じているのは経路の差し替えであって、直した入力で同じ経路へ出し直す
  ことではない。
- **報告して手番を返すことは、やり直しの代わりにならない。** やり直す余地が残っている間にユーザーの
  手番を挟むのは、判断を渡したのではなく作業を渡したことになる。
- 何度まで取り直してよいか・どこで諮るかは、実行中のスキルの再試行規定に従う。規定が無いなら、
  原因を特定できない・特定しても取り直しでは変わらないと分かった時点で諮る。

## 3. 対策を決める前に原因を確かめる

**何を見て止められたのかを確かめる前に、通すための書き換えを組み立てない。** 順序が逆だと、仮説を
否定する材料が出てからでも方針を捨てられなくなる(裏取りをどこまでやれば対策を書いてよいかは
[原因を裏取りしてから対策を書く](work-initiation.md#3-原因を裏取りしてから対策を書く)が正本)。

- **検査は理由を返す。** deny 理由・エラー文言・停止理由をまず読む。自分で仮説を立てるのは、検査
  自身が名指しした原因では説明が付かないと分かってからでよい。
- **裏取りの途中で仮説が否定されたら、その時点で仮説に基づく対策を捨てる。** 先に対策を決めていると、
  否定材料が出ても方針だけが残る。

## 4. 通すために成果物を変えない

**禁じるのは、内容が正しいまま検査を通すためだけに成果物を変えることである。** コミットメッセージ・
コード・仕様書・ユーザーへの報告を、通す目的で書き換えない。

**検査が名指しした不備がその成果物の側に実在すると裏取りできたなら、話は逆で、その成果物を直すことが
対処である。** 静的検査の指摘・テストの赤・規約違反はこれにあたり、直して通すのは本節がいう回避では
ない([対処の三つの終わり方](../rules/defect-followthrough.md#2-対処の三つの終わり方)の「直した」にあたる)。
分かれ目は、**成果物の側に直すべき不備が在ると裏取りできているか**である。

- **「原因を取り除く」と「ブロックを避ける」を取り違えない。** 検査が何を見て止めたかを確かめない
  まま成果物の側を変えて通す形は、後者にあたる。避けて先へ進むことがその停止の対処にならないことは
  [迂回は不具合の対処ではない](../rules/defect-followthrough.md#4-迂回は不具合の対処ではない)が正本。
- **成果物の側に不備が無いのに、変えなければ通らないと分かったなら、それは通してよい変更ではない。**
  止めて諮る。
- 委譲先に禁じられている回避を、呼び出し側が企図しない。禁止の趣旨は経路を変えても変わらない。

## 5. 削って通すのは直したことにならない

弾かれた入力を直すとき、**落とすのは弾かれた原因だけで、その入力が果たすべき目的は残す。**

- **削れば必ず通る。** よって「通ったかどうか」を基準に直すと、入力は毎回、検査を抜けるだけで目的を
  果たさない断片へ縮む。原因と目的が同じ部分に乗っているように見えるときほど、両者を分けて書き直す。
- 直した入力が目的を果たしているかは、通ったかどうかとは別に自分で確かめる。書いた直後に読み返し、
  **その入力が無くても困らない状態になっていないか**を見る。

## 6. 受理は目的を果たした証拠ではない

**検査は弾く条件を見るのであって、その入力が目的を果たしているかは見ない。** 通ったことを、正しく
なった証拠として扱わない。委譲先が受け取って先へ進んだことも同じで、受理は渡したものが役に立った
ことを意味しない。
